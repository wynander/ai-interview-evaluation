# Python exercise

LangChain support agent over synthetic local data (customers, orders,
subscriptions, documentation, incidents, tickets).

## Setup

```bash
uv sync
cp .env.example .env
```

Add the interview key to `.env`:

```text
OPENAI_API_KEY=<provided during the interview>
```

Model and Vercel AI Gateway base URL are fixed in `src/agent.py`.

## Run

**Interactive CLI**

```bash
uv run python -m src.main
```

**Evaluation**

Start from `eval-baseline.html` (open in a browser) instead of running the full
suite cold. It includes expected answers, rationale, and tool traces for all
18 cases. Each eval run overwrites that file.

```bash
uv run python -m src.eval
uv run python -m src.eval --verbose
```

Cases run concurrently. Each case times out after 2 minutes.

## Project layout

```text
src/
  agent.py            Agent definition, system prompt, AgentSession
  tools.py            Tool implementations exposed to the model
  data.py             Synthetic records (do not edit)
  runtime_helpers.py  Ticket state, message parsing, error formatting
  eval.py             18 scenario definitions and eval harness
  main.py             Interactive CLI
eval-baseline.html    Saved baseline report (regenerated by src.eval)
```

## Tools (starter)

| Tool | Purpose |
| --- | --- |
| `search_docs` | Lexical search over internal docs; returns 90-char snippets + metadata |
| `resolve_customer` | Lookup by name, email, or ID (substring name match) |
| `get_customer` | Full account record (plan/product/region codes) |
| `get_subscription` | Subscription by ID (`started_on`, cycle, status) |
| `get_orders` | All orders for a customer, newest first |
| `get_order` | Single order by ID |
| `get_active_incident` | Active incident by service + region (exact names) |
| `list_tickets` | Tickets for a customer, optional order/status filter |
| `create_support_ticket` | Create ticket; optional `related_order_id` (vague description) |

## Eval scenarios (18)

Two **controls** (basic lookup/history). The rest exercise distinct failure
modes:

| Mode | Cases |
| --- | --- |
| RAG | refund policy + deadline, renewal date, Growth/Starter seat limits, seat invoice timing, processing investigation threshold |
| Multi-turn RAG | Maya account → seat limit on her plan |
| Doc mapping | delayed order + incident, plan codes (GRW, ENT), Samira APAC incident, Jordan account → incident |
| Identity | ambiguous "Alex" |
| Tool schema | ticket linked to order (`related_order_id`) |
| State | existing migration ticket, duplicate ticket on create |

The HTML report shows **Expected answer** and **Why this case exists** for
each scenario. Eval checks positive outcomes (required facts in response/trace,
ticket counts, linked order IDs) — not specific phrasing of failures.

## Improvement hints

Think in layers rather than only editing the system prompt: retrieval quality,
tool contracts, multi-turn context, account/code vocabulary, and ticket state.
Inspect failing cases in `eval-baseline.html` (expected answer + traces) and
decide which layer is wrong.

Do not modify `data.py`.
